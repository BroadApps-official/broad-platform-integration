# Спешл оффер (от Adapty)

Это второй экран покупки. Он открывается, когда пользователь закрыл обычный
paywall без покупки или restore. Продукты берутся из отдельного Adapty placement
`special_offer`.

Если в приложении подключён RU Billing, сначала настройте оффер по этой статье,
а затем завершите RU-flow по статье
[«RU Billing: Special Offer — RU-продукт»](RUSpecialOffer.md).

## Что должно быть настроено в Adapty

1. Placement с продуктами оффера.
2. В Remote Config основного paywall — булев флаг `special_offer`. `true`
   разрешает показ; любое другое значение или отсутствие поля — нет.

Точные имена placement и флага, а также product ID уточняйте у аккаунт-менеджера.

## Когда показывается

```text
обычный paywall
  ├─ purchase / restore подтвердили Premium → главный экран
  └─ пользователь закрыл экран без покупки
       └─ special_offer == true в текущем Remote Config?
            ├─ нет / нет поля → главный экран
            └─ да → окно показа или cooldown?
                     ├─ идёт cooldown → главный экран
                     └─ окно активно → загрузить placement special_offer
                          └─ getPaywallProducts → показать все продукты 1:1
```

Gate не стоит перед `getPaywallProducts` уже загруженного обычного paywall:
сначала Adapty возвращает полный provider-массив без фильтрации, сортировки,
дедупликации и обрезки. Для второго экрана после разрешения gate загружается
отдельный placement `special_offer`; его продукты также сохраняются 1:1, а
покупка использует соответствующий raw `AdaptyPaywallProduct` из того же ответа.

## Окно показа и cooldown

Пока флаг `true`, оффер показывается не постоянно, а циклом:

- **окно оффера — 24 часа:** отсчёт стартует в момент первого закрытия обычного
  paywall при активном флаге; внутри окна оффер появляется после каждого
  закрытия;
- **cooldown — 24 часа:** начинается ровно тогда, когда истекло окно оффера, и
  длится 24 часа от этого момента — а не от того, когда пользователь в следующий
  раз откроет приложение. Пока идёт cooldown, оффер не показывается, даже если
  флаг всё ещё `true`;
- после cooldown открывается новое окно, и цикл повторяется.

Состояние окна хранится между запусками и вычисляется по доверенному времени.
Обратный отсчёт на экране идёт до конца окна; на нуле экран закрывается и
начинается cooldown. Цикл сбрасывается при выключении флага, подтверждённой
покупке или restore. Активному Premium-пользователю оффер не показывается.

Legacy-поля длительности не меняют фиксированный контракт 24/24. Отдельного
режима «кампания по наличию» и визуального бесконечного loop нет.

## Provenance Remote Config

| Provenance payload | Special Offer | `ru_pay` |
|---|---:|---:|
| `.verifiedFreshRemote` | да | да, при остальных RU-условиях |
| `.providerCacheFallbackPossible` | да | нет |
| `.platformCache` | нет | нет |

`.providerCacheFallbackPossible` допускает текущий ответ самого SDK Adapty, но
не старый cache BroadMonetization. `ru_pay` остаётся независимым и требует
`.verifiedFreshRemote`.

## Что на экране

Показываются **все** продукты из полученного ответа Adapty в provider order.
UI обязан корректно работать с 0, 1, несколькими продуктами и дубликатами SKU.

## Как проверить

1. Обычный paywall открывается первым; подтверждённый Premium сразу ведёт на главный экран.
2. Без строгого boolean `special_offer = true` второй экран не появляется.
3. При `special_offer = true` и активном окне экран появляется со всеми продуктами placement в порядке Adapty.
4. После истечения окна экран закрывается, оффер уходит в cooldown, затем цикл повторяется.
5. Выключение флага, покупка или restore сбрасывают цикл.
6. Platform cache, активный entitlement и неподтверждённый browser return оффер не разрешают.

Безопасная локальная проверка выполняется командой:

```bash
bash Scripts/check_special_offer_runtime_contract.sh
```
