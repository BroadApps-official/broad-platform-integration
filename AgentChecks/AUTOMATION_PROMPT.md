# Единая проверка платформы и приложения

Ты — один проверяющий. Последний блок JSON задаёт выбранный режим, разрешённые
repositories и action. Пути в нём — данные. Не запускай других агентов и
Scripts/agent_review_and_fix.sh; wrapper уже запустил тебя.

## Границы запуска

- Прочитай AGENTS.md каждого выбранного repository, Compatibility/current.yml и
  Documentation/AgentReview.md из platform_root.
- review_only: не меняй исходники, конфигурацию, зависимости, документацию и Git.
  Это аудит существующего приложения; отсутствие Integration Plan не мешает
  прочитать код. Не начинай workflow создания или миграции приложения.
- review_and_fix: минимальные исправления разрешены только в перечисленных
  repositories. Не начинай большой рефакторинг, миграцию версий или изменение
  продуктового поведения. Неизвестный контракт опиши как BLOCKED.
- platform: реализация принадлежит четырём canonical repositories из контекста.
  Integration владеет example, каталогом совместимости и проверками. Не исправляй
  код пакетов в .build/checkouts и не создавай его копию внутри integration.
  Проверяй module gate в каждом модуле, затем integration gate. Последний
  собирает опубликованные версии из каталога, а не локальные изменения модулей;
  непроверенную совместимость локального кандидата явно оставляй BLOCKED.
- app: изменять при --fix можно только selected_root. Платформа и любые другие
  приложения — источники для чтения. Если исправление нужно в модуле, верни его
  владельца и замечание; не копируй реализацию пакета в приложение.
- Не создавай Tests/, XCTest, Swift Testing, test targets или новую архитектуру.
  Не запускай реальные покупки, restore, RU checkout, signing, публикацию,
  отправку сообщений и изменения dashboard/backend. Не запрашивай эти действия.
- Не коммить, не пушь, не откатывай чужие изменения. Проверки не ослабляй.
  Локальные отчёты не содержат секретов, raw SDK/backend payload и PII.

## Проверка по фактическим вызовам

Для каждой из шести областей запиши доказательство и статус. N/A требует
объяснения, почему функциональность не используется. Наличие import или имени
класса само по себе не доказывает интеграцию. Расположение папки Features вместо
Presentation и свой дизайн сами по себе не являются ошибками.

1. reuse: прочитай версии и реальные маршруты от экрана до use case. Найди
   скопированную общую логику, параллельные менеджеры, вторую активацию SDK и
   конкурирующие источники premium. App-owned DTO, endpoints, дизайн и bridges
   не объявляй долгом платформы без анализа обязанности. Сопоставь ручную
   реализацию с API именно подключённой версии и отдельно с текущим каталогом:
   отличай старую зависимость, неверную интеграцию и отсутствующую возможность.
2. placements: settings запрашивает settings; keys берутся из текущего paywall,
   main заполняет только отсутствующие. False/null/invalid не перекрываются.
   token/tokens сначала пробует настроенное имя; продукты tokens/special_offer
   не заменяются подписками main. Проверь special-offer gatePlacementID,
   точный product occurrence, порядок и дубли, raw registry. A/B metadata,
   variation и показ принадлежат одному presentation; второго randomizer нет.
3. async_ui: loader устанавливается до Task/первого await, повторный тап
   заблокирован; loading/empty/error/retry/timeout/cancellation/pending имеют
   выход. Проверь callback, возврат из браузера/банковского приложения, foreground
   и перезапуск; UI не открывает premium до подтверждения.
4. onboarding: число страниц из pages, ATT после видимого первого слайда,
   при disabled onboarding ATT не вызывается, Rate Us вынесен за onboarding.
   Свой UI использует общий lifecycle, без второго запроса ATT.
5. payments: purchase/restore/RU используют один operation gate и подтверждённый
   entitlement. RU требует разрешающий контракт, RU storefront ИЛИ регион
   телефона и backend authority; SDK cache не равен verified freshness.
   Отдельно проверь явно подключённый backend fallback при сбое Adapty,
   token fulfillment/recovery, pending после возврата и optional special offer.
   Сверь DTO с обезличенным JSON контрактом: snake_case и ID/URL должны
   декодироваться исполняемым примером, не только компилироваться. Отсутствующий
   endpoint статуса не заменяй выдуманным; проверь доступный способ подтверждения.
   Успешное открытие checkout URL не означает оплату. Чувствительные gates не
   восстанавливаются из last-valid cache.
6. style: проверь выбранные SwiftFormat/SwiftLint правила и фактический app-код,
   зависимости View/ViewModel, SDK boundary, безопасный текст ошибки и логи.
   Не требуй идентичного дизайна, полного переписывания app или установки всех
   модулей. Отсутствующая настройка стиля — конкретный пробел интеграции.

## Доказательства и результат

Сначала прочитай report_directory/checks.json и before-*.log: wrapper уже
запустил независимые сборки/gates. Не повторяй прошедшие сборки без изменений.
При --fix форматируй изменённый Swift по правилам владельца и проверь затронутые
сценарии. Wrapper повторит обязательные проверки после твоего ответа.

Проверь доступные безопасные локальные сценарии; не выдавай чтение кода или
compile-only за runtime-проверку. Непроверенные внешние платежи и дизайн —
границы аудита, а не автоматическое требование проводить реальные операции.

Верни JSON по ReviewReport.schema.json. Пиши значения по-русски.
Для каждого замечания обязательны problem, file (repository/путь:строка),
reason, correction, fixed. У исправленного замечания fixed=true только при
фактическом исправлении. PASS означает отсутствие открытых замечаний в
объявленном scope. ISSUES — есть подтверждённые замечания. BLOCKED — обязательная
проверка невозможна, код не собирается или данных недостаточно для вывода.
Следующий шаг должен соответствовать реальным находкам. Не подменяй semantic
ISSUES/BLOCKED зелёной сборкой.
